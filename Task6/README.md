# Задание 6. Fitness-функции

Функции покрывают четыре требования: консистентность данных между сервисами, зависшие процессы, целостность Saga, таймауты и дедлайны. Ни одна функция не двигает деньги, пока их судьба не ясна. Сначала она сверяется с источником истины — банком или журналом операций Payment Service, — и только потом действует. Статусы — коды из [задания 2](../Task2/README.md). Функции спроектированы для рабочей системы. В прототипе ([Task4.2](../Task4.2/README.md)) две из них уже работают как тесты сборки: `BpmnSagaRules` — это тесты `ProcessModelTests`, `ProcessModuleIsolation` — тесты `ArchitectureTests`.

| Название функции | Назначение | Что проверяется | Действие при нарушении | Способ реализации |
| :- | :- | :- | :- | :- |
| `PaymentProcessConsistency` | Консистентность Payment Service и Camunda | Статус платежа совпадает с итогом процесса: `COMPLETED` — процесс завершается проведением, `REJECTED` — отказом. После конечного статуса процесс ещё рассылает уведомления, поэтому активный процесс у такого платежа — нарушение, только если он не завершился за 5 минут. У платежа в промежуточном статусе активный процесс есть. Платежи моложе 5 минут не проверяются: Operate читает данные из Elasticsearch с задержкой | Открывается кейс сверки для команды «Платёжные сервисы». Статус сам не исправляется: правильный итог устанавливают по банку | Задание по расписанию раз в 10 минут сравнивает платежи, изменённые за сутки, с экземплярами процесса из Operate API |
| `VerdictOutcomeConsistency` | Консистентность Payment Service и FraudCheck Service | Нет платежа `COMPLETED`, по которому FraudCheck Service записал запрет до перевода. По каждому запрету, пришедшему после перевода, запущен возврат постфактум | Алерт высокой важности командам «Безопасность» и «Платёжные сервисы». Если возврат постфактум не запущен, он запускается | Задание по расписанию раз в 10 минут сверяет решения из API FraudCheck Service с журналом операций Payment Service |
| `PaymentRequestWithoutPayment` | Консистентность входа | Запрос маркетплейса с ключом идемпотентности принят, а платежа по нему нет дольше минуты: сервис упал между приёмом и публикацией сообщения о старте или сообщение не привязалось к процессу | Алерт SRE. Маркетплейс на такой запрос получил 503 или не получил ответа и повторяет его с тем же ключом, повтор публикует сообщение заново. Если повторов нет дольше часа, платёж разбирают вместе с маркетплейсом: тела запроса у Payment Service нет, только его отпечаток | Задание по расписанию раз в минуту: SQL по таблице запросов Payment Service и сверка с платежами |
| `BankReconciliation` | Консистентность с банком | Заморозки, разморозки, переводы и возвраты в журнале Payment Service совпадают с выпиской банка за день | Алерт финансам, расхождение уходит в отчёт сверки, Payment Service заново запрашивает у банка статус операции | Ночное задание сверяет выписку банка с журналом операций по ключам идемпотентности |
| `StuckPaymentProcess` | Выявление зависших процессов | Сколько платёж находится в своём статусе. Для `CREATED`, `FUNDS_HELD`, `CHECKING`, `APPROVED`, `CUT_OFF_APPROVED`, `TRANSFERRING` и `RELEASING_FUNDS` порог — минута, это в десятки раз больше нормы с учётом повторов. Для `RELEASING_FUNDS` это значит, что SRE узнаёт о проблеме с разморозкой задолго до конца повторов. Для `IN_MANUAL_REVIEW` — 25 минут: 20 минут срока и запас. Для `TRANSFER_STATUS_UNKNOWN` — срок исполнения перевода. Отдельно проверяются открытые инциденты в Operate | Алерт дежурному SRE со ссылкой на экземпляр в Operate. Платёж не отклоняется по таймеру: сначала выясняется, на каком шаге он стоит | Запрос к журналу статусов Payment Service раз в минуту, метрика открытых инцидентов Zeebe в Prometheus |
| `StuckRefund` | Выявление зависших возвратов | Сколько возврат постфактум находится в своём статусе. Для `REFUND_REQUESTED`, `REFUNDING` и `RECOVERY_PENDING` порог — минута, как у денежных шагов платежа. Для `REFUND_STATUS_UNKNOWN` — срок исполнения возврата и запас на расхождение часов с банком. Для `REFUND_DETAILS_REQUESTED` — сутки без ответа клиента | По денежным статусам — алерт дежурному SRE со ссылкой на экземпляр в Operate. Если клиент сутки не указывает новые реквизиты, ему повторно уходит запрос, а возврат попадает в ежедневный отчёт финансам. Деньги в это время не двигаются: банк отклонил возврат, новый не отправлен, удержание с продавца не начато | Запрос к таблице возвратов Payment Service раз в минуту |
| `FrozenFundsWithoutProcess` | Выявление зависших денег | Сумма заморожена, а процесса по платежу нет или он уже завершён | Если платёж `REJECTED`, разморозка запускается повторно с тем же ключом. В остальных случаях открывается кейс сверки | Задание по расписанию раз в 10 минут: SQL по журналу операций Payment Service и сверка с Operate API |
| `CompensationIntegrity` | Целостность Saga по данным | У каждого `REJECTED` после заморозки есть разморозка. Нет платежа, который и переведён, и разморожен. У каждого `COMPLETED` ровно один перевод | Алерт высокой важности команде «Платёжные сервисы» и финансам | SQL-проверка журнала операций Payment Service раз в 10 минут: количество операций каждого типа на платёж |
| `BpmnSagaRules` | Целостность Saga на уровне схемы | У шага «Заморозить деньги» есть обработчик компенсации. Таймеры не ведут к компенсации. У перевода продавцу нет автоматических повторов, только уточнение статуса | Сборка Payment Service падает, схема не выкатывается | Тест в CI, который разбирает XML схемы |
| `ProcessModuleIsolation` | Целостность Saga на уровне кода | Денежный код Payment Service не зависит от клиента Zeebe и от модуля процесса. Обработчики процесса работают с деньгами только через API денежного модуля | Сборка Payment Service падает | Тесты ArchUnitNET в CI |
| `CheckCutOffRate` | Контроль сроков проверок | Доля автоматических проверок, завершённых по cut-off, за 15 минут. В норме cut-off — единичные случаи, поэтому стартовый порог — 2% проверок. Через месяц работы безопасность пересматривает его по фактической доле | Алерт SRE и безопасности: провайдер деградирует, и платежи проходят без его ответа | Счётчики проверок и срабатываний cut-off в Prometheus, правило алерта |
| `ManualReviewDeadline` | Контроль срока ручной проверки | Число задач оператора, у которых до истечения 20 минут осталось меньше 5 минут, и доля ручных проверок, закрытых по cut-off | Алерт дежурному смены безопасности: нужно добавить операторов, иначе платежи пойдут по cut-off | Запрос к Tasklist API раз в минуту и счётчики в Prometheus |
| `PaymentSla` | Контроль дедлайна платежа | 90-й перцентиль длительности всех успешных платежей — от старта до перевода, без уведомлений — за последний час меньше 5 секунд. Отдельно считаются перцентиль платежей без ручной проверки и доля платежей с ручной проверкой: если она подходит к 10%, SLA сорвётся при любой скорости автоматического пути | Алерт SRE. По Operate находится шаг, который замедлился. Рост доли ручных проверок уходит безопасности | Гистограмма длительности и счётчик ручных проверок в Prometheus по событию перевода, правила алерта |
